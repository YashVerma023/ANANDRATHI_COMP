03

POS / INT classification

per cycle × index × user × algo
POS account traded on any non-0DTE day of its cycle INT account traded on 0DTE only

That single rule covers every case without special-casing:

  • NF 4DTE + 1DTE + 0DTE → POS
  • NF 1DTE + 0DTE, Friday holiday, no 4DTE → POS
  • SX 1DTE + 0DTE → POS
  • 0DTE only → INT
  • a cycle where no non-0DTE day ran at all → everyone is INT, automatically

Written to MainData as Running Type; the AccountType sheet carries one row per account-cycle with its DTE set. Result: 5,628 INT and 4,408 POS account-cycles.

Terminal check

Any NF cycle running 0DTE alone (both 4DTE and 1DTE missing — two holidays in one Fri–Tue window) is dumped in full to the terminal for manual review. None occur in the current data.

04

Allocation backfill

73 rows · 58 accounts

The 0DTE row is the reference for its whole cycle. Within each cycle × index × user × algo, every non-0DTE row takes the account's 0DTE allocation — the SX 1DTE row, and the NF 4DTE and 1DTE rows.

Allocation is replaced in place with no original retained, and MTM % is recomputed as MTM / new Allocation × 100 so the column stays consistent with it.

Guard

If an account ever shows two different 0DTE allocations inside one cycle, the script raises rather than silently picking one.

An account-cycle with 1DTE/4DTE rows but no 0DTE row has no reference allocation, so the entire account-cycle is dropped — printed to the terminal first. Six rows, five account-cycles:

05

Normalisation to 1 Cr

so size cannot dominate
factor = Allocation / 1,00,00,000 Norm Allocation = 1,00,00,000 Norm MTM = MTM / factor Norm MTM % = Norm MTM / 1,00,00,000 × 100

A 2 Cr account contributes 1 Cr of allocation and half its MTM; a 5 Cr account one fifth.

Why row-level MTM % is unchanged

MTM % is a ratio, so scaling both numerator and denominator cancels out. Normalisation only bites once MTM is summed across accounts of different sizes — which is exactly what the next step does.

06

Cycle MTM %

CycleMTM sheet · 206 rows

Computed per cycle × index × algo × running type:

Total_Allocation = Σusers ( that user's average Norm Allocation across the days it ran in the cycle ) Cycle MTM % = Sum_MTM / Total_Allocation × 100

Why the per-user average comes first: a user counts its full 1 Cr once per cycle, however many days of that cycle it traded. A POS account running 4DTE+1DTE+0DTE and one running only 1DTE+0DTE both contribute 1 Cr. The denominator measures capital deployed, not capital-days.

Worked example — NF_2026-05-12, Algo 1, POS

67 users in the cycle; 49 ran all three days, 18 ran only two. Each user's average allocation is 1 Cr, so Total_Allocation = 67 × 1 Cr = ₹67,00,00,000. With Sum_MTM = ₹4,10,62,080, the Cycle MTM % is 6.13.

Columns: Month, Cycle, Index, Algo, Running Type, Sum_MTM, Days, Accounts, Rows, Total_Allocation, Cycle MTM %.

07

The two pivot methods

they answer different questions

Sum daily mtm%

Σ ( Cycle MTM % ) over the group

Adds per-cycle ratios. Every cycle counts equally, however many accounts ran in it.

Avg daily mtm%

Σ Sum_MTM ——————————————— mean( Total_Allocation )

Pools the raw MTM instead, so cycles with more accounts carry proportionally more weight.

Reading them together

The two will not agree, and where they diverge sharply the cause is usually a cycle with an unusual account count — see issue 01 below. The Avg figure also scales with cycle count: MAY-26 spans seven cycles and SEP-26 only one, so those two cells are not directly comparable. The Sum column has no such property.

Month assignment. A cycle belongs to the month of its 0DTE (expiry) day. An NF cycle whose 4DTE falls in July but whose 0DTE falls in August counts entirely as August. Months are labelled MMM-YY so multi-year data cannot collide.

!

Known data issues

verify before relying on these figures

01 NF_2026-08-11 is a thin cycle

70 distinct accounts against 178–220 in every other cycle — 8 accounts on 4DTE and 12 on 1DTE for Algo 1, against 30 on 0DTE, and Algo 15 has no 4DTE or 1DTE rows in it at all. Because the Sum method weights every cycle equally, this partial cycle swings the AUG-26 figures hard, which is exactly why Sum and Avg diverge most in that month (Algo 1 INT: +1.55 against −0.60). It reads as a partial data capture for 07-Aug and 10-Aug rather than a real trading pattern.

02 Eleven Anand Rathi IDs are missing

76 of the 87 listed IDs reach MainData. The rest were either removed by steps 01–04 or never appear in the source file.

03 NS0008 ran 4DTE and 1DTE with no 0DTE

In NF_2026-08-04 — a combination that should not occur. Dropped by step 04, but worth checking whether the 0DTE row is missing from the source or the account squared off early.

04 MAY-26 and SEP-26 are partial months

SEP-26 holds a single cycle, NF_2026-09-01, the last in the data, so its figures are not comparable with a full month's.

¶

Design notes

  • Nothing is silently corrected. Every drop is logged with its count, every anomaly is printed, and contradictory input raises instead of guessing.
  • Timestamped output — runs never overwrite each other.
  • CycleMTM is the audit trail. Every pivot cell traces back to it.
  • If Excel reports “file format is not valid”, the workbook was opened while it was still being written — a 5 MB file takes about 12 seconds. Wait for the Wrote … log line, then delete any leftover ~$….xlsx lock file.
